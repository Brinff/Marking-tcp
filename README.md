# Marking TCP

Тестовое задание: две независимые консольные программы на C# / .NET 10, взаимодействующие по TCP.

- **Marking.Server** каждые 500 мс генерирует случайный код маркировки в формате GS1 и отправляет его подключённым клиентам.
- **Marking.Client** подключается к серверу, принимает коды и дописывает их в файл. При разрыве соединения переподключается сам.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Windows, Linux или macOS

Сервер и клиент это два отдельных приложения со своими `Program.cs` и запуском. Общий код протокола вынесен в библиотеку `Marking.Protocol`, чтобы формат сообщений не дублировался.

## Запуск

Сначала сервер (в первом терминале):

```bash
dotnet run --project src/Marking.Server
```

Затем клиент (во втором терминале):

```bash
dotnet run --project src/Marking.Client -- --output out/codes.txt
```

Порядок не важен: если клиент запущен раньше сервера, он будет повторять попытки подключения.

Остановка: `Ctrl+C` в соответствующем терминале (корректное завершение, код возврата 0).

## Формат кода маркировки (GS1)

Генерируется российский формат (структура, как у кодов «Честный ЗНАК»). Значения случайные и в реальных системах недействительны.

```
01 GTIN(14)  21 серийный номер(20)  <GS>  91 ключ(4)  <GS>  92 подпись(44)
```

| AI   | Содержимое | Генерация |
|------|-----------|-----------|
| `01` | GTIN, 14 цифр, последняя контрольная | 13 случайных цифр + контрольная цифра по алгоритму mod 10 (веса 3, 1, 3, 1, ...) |
| `21` | серийный номер, 20 символов | случайные `A-Za-z0-9` |
| `91` | ключ проверки, 4 символа | случайные `A-Za-z0-9` |
| `92` | код проверки, 44 символа | Base64 от 32 случайных байт |

`<GS>` это управляющий символ GS (ASCII `0x1D`). Он ставится после полей переменной длины (`21`, `91`), за которыми идёт ещё одно поле. После `01` (фиксированная длина) и после последнего поля `92` его нет. Итоговая длина кода 92 символа.

## Протокол обмена

TCP является потоком байт и не сохраняет границы отдельных отправок: несколько записей могут прийти одним чтением, а одна запись несколькими. Поэтому каждое сообщение передаётся с префиксом длины:

```
[ 4 байта: длина N, big-endian ][ N байт: UTF-8 строка кода ]
```

Пример для строки `hello`: `00 00 00 05 68 65 6C 6C 6F`.

- Допустимая длина N: от 1 до 1024 байт. Значение проверяется **до** выделения буфера, поэтому мусор в заголовке не приводит к огромной аллокации.
- Получатель дочитывает ровно N байт в цикле (одно чтение может вернуть меньше).
- Ноль байт на границе сообщения означает чистое закрытие соединения. Ноль байт посреди сообщения означает обрыв и `ProtocolException`.
- Некорректная длина и невалидный UTF-8 приводят к `ProtocolException`, клиент закрывает соединение и переподключается.
- Соединение однонаправленное: сервер пишет, клиент читает.

По сети передаётся настоящий символ `0x1D`, замена на `<GS>` делается только в файле и в логах.

## Поведение сервера

- Принимает **несколько клиентов одновременно**. У каждого своя сессия с очередью (ёмкость 100) и своим циклом отправки, поэтому медленный клиент не тормозит остальных.
- При переполнении очереди отбрасываются самые старые коды (`DropOldest`).
- Генератор тикает каждые 500 мс (`PeriodicTimer`, без накопления дрейфа). **Если клиентов нет, сгенерированный код отбрасывается.** Коды за время между отключением и переподключением клиента теряются.
- Отключение клиента замечается сразу: сессия параллельно с отправкой держит чтение сокета и реагирует на закрытие.
- После отключения сессия удаляется из реестра, сокет закрывается.
- Для сокетов включены `NoDelay` и `KeepAlive`.
- Ошибка занятого порта при старте сообщается и завершает программу, а не проглатывается.
- Ошибки `accept` логируются, цикл продолжает работу после паузы в 1 с.

## Поведение клиента

- Для каждой попытки создаётся новый `TcpClient`.
- Пауза между попытками растёт экспоненциально: 1 → 2 → 4 → 8 → 10 с (максимум 10 с). После получения первого кода пауза сбрасывается до 1 с.
- Файл открывается один раз на всё время работы клиента (`FileMode.Append`, `FileShare.Read`) и не закрывается при переподключениях. После каждого кода выполняется сброс буфера (`AutoFlush`), поэтому при падении процесса записанные коды не теряются.
- Кодировка файла UTF-8 **без BOM**, строки разделены `Environment.NewLine`.
- **Символ GS в файле записывается как `<GS>`** для читаемости. Пример строки файла:

  Реальный вид: `01<GTIN>21<20 символов><GS>91<4 символа><GS>92<44 символа>`.
- Ошибки сети (`SocketException`, `IOException`), нарушения протокола и закрытие сервера приводят к переподключению. Ошибка записи в файл считается фатальной: клиент завершается с кодом 1.

## Обработка ошибок и завершение

| Ситуация | Реакция |
|----------|---------|
| Сервер закрыл соединение (чтение вернуло 0) | клиент логирует и переподключается |
| Обрыв (`IOException`, `SocketException`) | клиент логирует и переподключается |
| Сервер недоступен | повторные попытки с нарастающей паузой |
| Битый заголовок или UTF-8 | `ProtocolException`, переподключение |
| Клиент отключился | сервер удаляет сессию и освобождает сокет |
| `Ctrl+C` | `CancellationToken` пробрасывается во все `await`, сокеты, файл и логгер закрываются через `using` / `await using` |

## Логирование

Используется `Microsoft.Extensions.Logging.Console` (**сторонняя NuGet-зависимость** в проектах сервера и клиента). Уровень логирования по умолчанию `Debug` (каждый сгенерированный и полученный код пишется в лог, GS выводится как `<GS>`). Уровень меняется в `Program.cs` через `SetMinimumLevel`.

## Тесты

```bash
dotnet test
```

Покрыто:

- **Framing:** склеенные сообщения, побайтовая доставка, обрыв в заголовке и в payload, некорректная длина, невалидный UTF-8, отмена.
- **GS1:** контрольная цифра, формат кода, количество разделителей, воспроизводимость по seed.
- **Сервер:** доставка кодов, очередь с отбрасыванием старых, отключение и повторное подключение клиента, остановка по токену (интеграционные тесты на реальных сокетах loopback).
- **Клиент:** запись кодов по порядку, склеенные сообщения, переподключение после закрытия и после нарушения протокола, запуск раньше сервера, отмена.
- **ReconnectPolicy** и **CodeFileWriter** (создание папок, дозапись, отсутствие BOM, сброс на диск).

## Ограничения

- **Half-open соединения** (пропала сеть без FIN/RST): KeepAlive настроен (первая проверка через 30 с, интервал 10 с, 3 попытки), разрыв обнаруживается примерно за минуту; быстрее обнаружить можно таймаутом тишины.
- Нет TLS и аутентификации, протокол рассчитан на доверенную сеть.
- Коды, сгенерированные в отсутствие клиентов, не буферизуются и не доставляются позднее.
- Сброс буфера гарантирует передачу данных ОС, но не защищает от потери данных при отключении питания (для этого нужен fsync).
